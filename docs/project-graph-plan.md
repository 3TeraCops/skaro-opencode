# Граф проекта: план реализации и приёмки

Дата: 21.10.2026. Статус: реализация поручена владельцем; этапы ещё не приняты.
По последующему прямому поручению владельца подготовлено отдельное визуальное
превью живой карты на Sigma.js с настоящими компонентами Skaro и C4 Chatballs.
Это исследование PG-0 не закрывает этапы полной реализации. Сейчас добавлены
продуктовые разделы и отдельный фоновый индекс; полнота проверок фиксируется ниже.
По поручению от 21.10.2026 реализуется полная спецификация. C4/граф расположены
в основном меню после задач; внешний вид основан на превью с правками владельца.

## Текущее состояние реализации

- Контракты: `packages/core/src/graph/`, типизированный IPC `shared/graph.ts`.
- Индекс: `main/graph/` — SQLite/WAL, отдельные index/query workers, очередь,
  отмена, восстановление, watcher, сверка manifest и обзор до открытия раздела.
- Анализаторы: TypeScript Compiler API, Svelte AST, Python Tree-sitter/WASM,
  Django URLConf/ORM, HTTP-клиенты, регистрации событий/IPC/MCP, Compose,
  Markdown и проекция принятой C4. Динамические цели остаются unresolved.
- UI: `renderer/src/graph/`; отдельный C4 переиспользует `C4Scene` и текущий
  просмотрщик. Дополнительные управления утверждены в
  [решении по компоновке](project-graph-controls.md).
- Проверка настоящего Chatballs подтвердила фоновое построение до открытия
  раздела: снимок `graph-1.0.5` содержит 24 040 узлов и 120 877 связей.
  Это результат конкретного checkout, а не фиксированные значения продукта.
- Целевые проверки и визуальная сверка описаны в
  [протоколе проверки](project-graph-verification.md). Полная приёмка всех
  платформ и бюджетов производительности ещё не завершена. Автономное
  HTML-превью не считается подтверждением работоспособности полного индекса.

Основания: [спецификация](project-graph.md), [индекс](project-graph-index.md),
[сценарии](project-graph-scenarios.md), действующие [C4](c4.md) и [baseline](ui-baseline.md).
Идентификаторы PG-* локальны этому плану, не являются созданными задачами Skaro.

## 1. Исходное состояние и точки интеграции

В Skaro уже есть @xyflow/svelte, elkjs, C4-модель v1 и её валидация,
полноэкранный просмотрщик, превью документов, get_c4_context/propose_c4/review_c4,
фоновое выполнение части операций и типизированный IPC.
Наличие этих частей не означает реализацию общего графа или его индекса.

| Область            | Существующая точка входа                                              | Планируемое действие                                                                      |
| ------------------ | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Модель C4          | packages/core/src/c4/                                                 | Переиспользовать IDs, c4AtState и валидацию без изменения v1                              |
| Главное меню       | renderer/src/screens/ProjectNavigation.svelte и ProjectSection.svelte | Добавить C4 и граф после задач; в дереве документов оставить ADR, спецификации и «Прочее» |
| Документы          | renderer/src/docs/DocsScreen.svelte, docs-controller.svelte.ts        | Разделить document/c4/graph, сохранить leave-flow                                         |
| Просмотрщик        | renderer/src/c4/                                                      | Общие входы из дерева/превью, совместимые обратные переходы                               |
| Фоновая работа     | main/background/client.ts и protocol                                  | Отдельная очередь индексации с отменой/бюджетами                                          |
| Завершение импорта | main/import-apply.ts и imports.ts                                     | Сохранённая идемпотентная постановка построения после успешного применения импорта        |
| IPC                | shared/ipc*.ts, ipc-channels.ts, preload/index.ts                     | Валидированные graph-запросы/события                                                      |
| Артефакты          | main/project-artifact-watch.ts                                        | Инвалидация C4/docs; отдельное наблюдение исходников                                      |
| Навигация          | app-navigation.svelte.ts, WorkspaceState, docs preferences            | Версионированное восстановление назначений/камеры                                         |

Пути renderer/src, main и shared здесь относятся к apps/desktop/src.
На момент подготовки рабочее дерево содержит многочисленные посторонние правки.
Перед реализацией перечитать актуальные источники и сохранить изменения владельца;
не откатывать их и не переносить старые предположения о структуре файлов.

## 2. Структура реализации

Ниже — рекомендуемое распределение ответственности; окончательные имена модулей
фиксируются до кода, зависимости направлены от UI к сервису и доменному контракту.

| Модуль/каталог                            | Единственная ответственность                                                  |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| packages/core/src/graph/model, validation | Browser-safe DTO, идентичность и проверки снимков                             |
| packages/core/src/graph/index, storage    | Manifest, снимки, транзакции и запросы к кэшу                                 |
| packages/core/src/graph/analyzers/        | Отдельные language/framework адаптеры и resolver                              |
| packages/core/src/graph/projections/      | C4, документы, группировка, provenance и покрытие                             |
| apps/desktop/src/main/graph/              | Scope, scheduler, watcher, IPC и source access                                |
| renderer/src/graph/                       | Композиция экрана и отдельные search/details/filters subviews                 |
| renderer/src/graph/rendering/             | Sigma adapter, стили, geometry и particles lifecycle                          |
| renderer/src/graph/layout/                | Worker раскладки, мягкое движение с сохранением структуры и локальные позиции |
| renderer/src/graph/playback/              | Машина состояний, часы и проекция текущего шага                               |

Page-компонент не владеет парсером, запросами, layout и проигрывателем одновременно.
Компоненты около 180 строк разделяются; новый/изменённый файл не должен расти
за примерно 300 строк. Анализаторы TS, Python, Django, HTTP и events не объединяются
в один универсальный файл. Общие типы не импортируют Electron/fs в renderer.

## 3. Этапы и зависимости

Порядок критического пути: PG-0 → PG-1 → PG-2 → PG-3 → PG-4 → PG-5 → PG-6 → PG-7.
Декомпозиция не разрешает делегирование агентам и не меняет правила владельца.

### PG-0. Уточнить контракты и утвердить дизайн

- Зафиксировать текущие точки интеграции, совместимые версии Sigma/Graphology,
  способ упаковки WASM, worker, SQLite и поддерживаемые release-архитектуры.
- Согласовать карту состояний, внешний вид по разделу 7 спецификации и RU/EN.
- Утвердить reference hardware/данные и измеримые бюджеты из раздела 7 плана.
- После отдельного поручения на код проверить в настоящем Electron совместимость
  Sigma, частицы, resize/dispose и контуры на реальной модели Chatballs.
- Выделить неподтверждённые API и риски. Не считать чужой пример доказательством.

Выход: утверждённые дизайн/контракты и протокол технической проверки.
Без визуального baseline UI-часть не начинается; подготовка текущих документов
не означает прохождение этого gate. Новые UI-решения не дорисовываются в коде.

### PG-1. Модель, снимки и кэш

- Реализовать DTO/schema, IDs, evidence, coverage, current/planned и multiedges.
- Подготовить индексный SQLite-кэш отдельно от C4/AppDb и миграции его версии.
- Реализовать manifest HEAD+dirty+untracked, root/worktree identity и generation.
- Добавить атомарное построение/публикацию, отмену и восстановление после прерывания.
- Подготовить bounded queries, курсоры, поиск и ограничение ресурсов.

Выход: повторяемый индекс реальных файлов без UI, записи в проект и runtime-import.
Проверки: стабильность IDs при чтении, различие checkout, целостность snapshot,
непринятие устаревшего результата, корректное неполное покрытие.
Покрывает G-08, G-09, G-17—G-19, G-22, G-24.

### PG-2. Анализаторы реализации и межслойные связи

- TS/JS/TSX/JSX: imports/exports, области, symbols, aliases, calls/references.
- Svelte: AST script/template, ссылки компонентов/handlers, исходные диапазоны.
- Python: parser, модули/области, imports/inheritance/calls и unresolved.
- Django/HTTP: URLConf, views, ORM relations/reads/writes и статические запросы.
- Events/IPC/MCP: отдельные правила реестров Chatballs и каналов Skaro.
- Compose: deploy-структура без выдуманной сетевой активности.
- C4/Markdown: documents, SPEC R-n, ADR, tasks/milestones и явные bindings.
- Зафиксировать таблицу покрытия и доказательств на Chatballs и Skaro.

Выход: все обязательные адаптеры работают; код, модель и документы соединены.
Одних C4/imports недостаточно. Для неопределимых целей есть диагностика.
Проверки: реальные URL→handler, HTTP→endpoint, event→consumer, model relations,
alias/re-export и диапазоны; точность на вручную сверенной выборке.
Покрывает G-04—G-09, G-12, G-23.

### PG-3. Сервис, обновления и запросы

- Отдельная очередь фоновых работ, scheduler и source watcher с reconciliation.
- Автоматическое построение сразу после успешного завершения импорта, без открытия
  графа; сохранённая идемпотентная постановка не задерживает результат импорта.
- Наблюдение кода/документов/C4 независимо от выбранной вкладки и активности проекта;
  закрытие графа не останавливает обновления, удаление проекта останавливает.
- Восстановление очереди и фоновая сверка manifest при запуске Skaro, включая
  изменения во время выключенного приложения и импортированные проекты без индекса.
- IPC, валидация scope/cursor, отмена, progress, stale/partial и bounded DTO.
- neighbors/path/impact с типами, направлением и достоверностью доказательств.
- Инкрементальная инвалидация зависимых файлов/aliases/registries и смены ветки.
- Переход к source с проверкой realpath/hash и безопасным диапазоном.

Выход: renderer может читать согласованные порции, агент/документы не блокируются.
Проверки: соответствие инкрементального и полного индекса одного checkout,
предотвращение cross-project доступа, изменения во время чтения и перезапуск;
успешный импорт без открытия графа, отсутствие запуска для непринятого/неуспешного
импорта, повтор события без дубля, обновления при другом активном проекте,
догоняющее обновление после перезапуска и ошибка индекса без отката импорта.
Покрывает G-10—G-12, G-17—G-19, G-21, G-22, G-24.

### PG-4. Раздел C4 и маршрутизация документации

- Два новых пункта основного меню после задач, с существующими компонентами навигации.
- Существующий C4 viewer доступен из раздела и прежних документальных превью.
- Переходы C4/graph/document, несколько представлений элемента и leave-flow.
- Версионировать восстановление состояния, сохранить обычные document paths.

Выход: самостоятельный раздел C4 и вход графа в согласованном месте.
Проверки в штатном Electron: порядок, раскрытый ADR, несохранённый документ,
превью, назад, полный экран, перезапуск и отсутствие модели.
Покрывает G-01—G-03, G-20, G-25. Сам граф ещё не считается поставленным.

Выход: исследуемый полный индекс, не только архитектурная демонстрация.
Проверки: реальные источники обоих проектов, все разрешённые переходы,

## 4. Согласование существующих контрактов

Сейчас c4.md определяет диаграмму как вложение документа. Новое требование
добавляет самостоятельный вход, сохраняя вложенные превью. При реализации
этот пункт должен быть явно обновлён, остальные гарантии C4 сохраняются.
Никаких миграций C4 v1 ради цветов, координат, частиц или проигрывателя.

Не менять действующие get_c4_context/propose_c4/review_c4 и submit_result/merge_task
ради чтения индекса. Read-only MCP graph-инструменты могут быть отдельным будущим
расширением; они не требуются для UI и не входят скрыто в текущий объём.
Не подключать автоматические «исправления архитектуры» или новые приёмочные блокеры.

## 5. Риски и решения

| Риск                                                 | Решение и критерий остановки                                                               |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| WebGL/частицы несовместимы с закреплённой Sigma      | PG-0 на настоящем Electron; при невозможности сообщить blocker, не менять библиотеку молча |
| Динамический Python/Django не разрешается статически | Узкая доказательная семантика и unresolved; не обещать 100% call graph                     |
| UI превращается в нечитаемый клубок                  | Группировка, раскрытие, фильтры и ограниченная материализация с доступом ко всему индексу  |
| Парсинг блокирует агента/ответ владельца             | Отдельная очередь, ограниченный pool и приоритет интерактивных запросов                    |
| Файлы меняются во время обхода                       | Hash/generation, retry/cancel и атомарная публикация                                       |
| Новый индекс конфликтует с C4                        | Только производные факты; расхождение видно, принятую модель не менять                     |
| API примеров отличается от релиза                    | Версии/лицензии/worker assets фиксируются до реализации                                    |
| Нет согласованного визуального состояния             | Остановить зависимый UI-этап и получить baseline; не создавать временный продуктовый UI    |

## 6. Данные проверки

Основной пример — настоящий Chatballs по пути из спецификации, в режиме чтения.
Второй — Skaro: TS/Svelte, Electron IPC и MCP. Данные охватывают разные стеки.
До проверки записываются HEAD, dirty fingerprint, C4 hash/revision и coverage.
После сверяется отсутствие записей индексатора в оба checkout.
Числа revision 2 используются как исходная справка, а не hardcode в тестах.

Не создавать mock API, fake backend, HTTP-серверы, fixtures, seed или изменённые
модели Chatballs ради демонстрации. Негативные интеграционные проверки, которым
нужны изменения файлов/корней, требуют отдельно разрешённого настоящего checkout;
без него фиксируется непроведённый сценарий, проверка не подменяется заглушкой.

## 7. Предлагаемые бюджеты для PG-0

Метрики измеряются в штатной сборке Electron, на записанных CPU/RAM/GPU/OS,
с версиями анализаторов и реальным размером индекса. Пороги ниже — целевые
предложения для утверждения, не результаты проведённых измерений.

| Метрика                                       | Цель                                         |
| --------------------------------------------- | -------------------------------------------- |
| Открытие кэшированного архитектурного обзора  | p95 ≤ 1 с после готовности оболочки          |
| Поиск/соседи/детали, первая порция            | p95 ≤ 200 мс без cold index                  |
| Реакция выбора/управления шагом               | p95 ≤ 100 мс                                 |
| Pan/zoom/частицы на согласованном подграфе    | p95 времени кадра ≤ 33 мс                    |
| Полный cold index Chatballs                   | ≤ 60 с на утверждённой машине                |
| Обновление после одного обычного source-файла | ≤ 3 с после debounce, без смены конфигурации |
| Дополнительная память index+renderer+layout   | ≤ 512 МиБ на согласованном наборе            |
| Остановка по отмене                           | ≤ 1 с, без публикации отменённой generation  |

Проверяются 10 циклов открыть/закрыть граф/сценарий и отсутствие устойчивого роста
памяти, listener/workers и активных кадров после dispose. При большем реальном
проекте показывается честное покрытие/лимит; индекс не обрезается незаметно.

У каждого G-ID фиксируются этап, проверка, результат и ссылка на доказательство;
обязательное поведение без подтверждения не отмечается выполненным.
Для значимых изменений кода перед «готово»/коммитом — штатная сборка и только
тесты изменённого поведения/непосредственно затронутых сценариев. UI дополнительно
проверяется в браузерном контексте настоящего Electron со штатным main/IPC.
Мелкие UI-правки и полный прогон — строго по правилам корневого AGENTS.md.
Для отдельной документационной правки сборка/runtime-тесты не требуются;
код визуального превью проверяется сборкой и затронутыми Electron-сценариями.
