# Подготовка кандидата Skaro 2.1.2

Дата: 20.10.2026. Это запись локальной подготовки, не подтверждение публикации.
Последний публичный релиз на момент начала подготовки — 2.1.1.
Версии комплекта и продукта кандидата — 2.1.2.

Сжатие строк документов исправлено. При подготовке также воспроизведена и
устранена гонка стартового чтения SQLite-кеша: окончательный локальный пакет
прошёл пять чистых запусков без retries и пять проверок сохранённого проекта.
Сборка, типы и lint прошли. Финальные CI и шесть платформ проверяются на новом
commit после исправления; прежние комплекты ниже сохраняются только как история.
Релиз не опубликован.

## Разрешённый контур

Владелец разрешил полный прогон существующих тестов с fixtures и временными
HTTP test servers, запретив новые вызовы моделей. Опциональные реальные
agent/canary проверки не включаются. Chatballs не запускается и не изменяется.
Для browser-проверок используется только проект
`dc52bd5f-1cd6-4705-adbd-7ffebb8540b6`,
`output/performance-write-isolated/project` и его отдельный профиль.

## Исправление дерева документов

Ранее `.item` и `.group` могли сжиматься во flex-контейнере при переполнении.
На настоящем UI строка уменьшилась с 32 до 19,25 px. В `doc-tree.css`
добавлен `flex: none` для строк и заголовков: исходные размеры 32/28 px,
типографика, отступы и порядок сохранены. Список прокручивается.

`doc-tree-size-live.spec.ts` проверяет раскрытие групп с реальным документом
при масштабе 100–500%, включая переполнение панели. После исправления все
строки — 32 px, заголовки — 28 px. Проверены браузерные размеры и скриншот
штатного интерфейса; данные и API не подменялись.

## Изменения, необходимые для предрелизных проверок

- Загрузчик background worker теперь определяет настоящий собранный файл
  без зависимости от Electron `app`. В source-level Node-проверках запускается
  тот же скомпилированный worker. Отсутствие сборки остаётся явной ошибкой.
- В CI и release workflow сборка выполняется до storage integration тестов.
- Существующие тестовые профили используют штатное имя `skaro.db`; завершение
  fixture закрывает background workers до удаления её файлов.
- Проверка legacy-миграции начинает с настоящей версии 4; новая версия схемы — 8.
- Golden-вопрос остаётся `waiting`; незакрытая карточка не показывает завершение
  работы. Проверки согласованы с утверждённым требованием, а не с прежним idle.
- ESLint имеет явный корень конфигурации и исключает временный `output`.
- Результат задачи напрямую уведомляет планировщик автоматического завершения;
  необязательный следующий обход больше не требуется. Уведомление не запускает
  ещё не стартовавший monitor.
- Остановка процесса дожидается начатой асинхронной регистрации OS identity;
  подтверждение регистрации ждёт параллельного завершения дерева. Это сохраняет
  родителя до остановки потомков и объединяет повторные stop для одного запуска.
  Проверка birth/platform перед остановкой сохранена.
- При завершении completion service теперь дожидается начатого обхода проектов
  и чтения Git HEAD, прежде чем разрешить закрытие базы. Прежнее отключение
  таймера не завершало уже выполняющийся обход. Гонка воспроизведена отдельным
  тестом на реальных Git/SQLite существующего CompletionFixture:
  `output/release-prep-lifecycle-before.log` — активное чтение после close
  и необработанное обращение к закрытой базе. Никакие результаты Git не подменялись.

разрешил CI-сборку без публикации. Все шесть платформ собраны на native CI

пользовательской установки не выполнялись. Проект описания релиза с шестью
прямыми ссылками: [release-2.1.2.md](release-2.1.2.md).

## Синхронный bootstrap и подключение DevTools

Release CI `39461972496` на `0bf8e5c87062bb42fb4ac4950f133a638da87250`
собрал шесть платформ и общий manifest. Штатный PR CI `39461977609` прошёл
Linux/macOS, но Windows дважды остановился на `electron.launch` (90 секунд).
Отказ воспроизведён локально на настоящем пакете с новым пустым профилем:
`output/release-prep-clean-window.log`. Повторная попытка прошла; такой результат
не считается устойчивым успехом.

`output/release-prep-clean-protocol.log` сохраняет настоящий CDP: браузер отвечает,
но команды страницы останавливаются при подключении к уже загружающемуся preload.
Прямой запуск того же пакета без автоматического подключения Playwright показал
окно за 0,81 s (`release-prep-clean-diagnostic.log`). Попытка применить loader
Playwright дала 4 passed / 1 failed и отменена; production-пакет под тесты
не подменяется, тайм-ауты не повышаются.

Стартовый снимок переведён с `ipcRenderer.sendSync` на асинхронный запрос,
независимый от инициализации остальных сервисов. Renderer получает его до
импорта экранов; данные и кеши первого экрана сохранены. Reload заново запрашивает
актуальное состояние main. Проверка сохранённого окна дополнена сменой раздела
и reload. Production build прошёл (`release-prep-bootstrap-build.log`), типы
main/renderer без ошибок и предупреждений, lint прошёл.

После удаления синхронного ожидания исчез 90-секундный тайм-аут, но в одном из
пяти запусков остался пустой DOM. Настоящий протокол
`output/release-prep-clean-bootstrap-protocol.log` установил точную причину:
`cachedProjectCards` выбрасывал `database is locked` при одновременном создании
`registry.db` фоновым worker. В синхронном bootstrap это также оставляло preload
без ответа; ошибка не была просто медленным выполнением теста.

Первый ограниченный снимок теперь читается до старта фоновых служб. Повторное
чтение кеша обрабатывает только SQLite BUSY/LOCKED без ожидания; остальные
ошибки не скрываются. Основной индексированный запрос по-прежнему возвращает
все карточки и содержимое. `output/release-prep-startup-cache-lock.log`:
1 passed — настоящий ProjectIndex и SQLite EXCLUSIVE lock в существующем
CompletionFixture; после освобождения читаются все прежние данные.
Новые browser-проверки и финальные CI фиксируются после завершения.
