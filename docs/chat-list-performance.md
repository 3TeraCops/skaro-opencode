# Список чатов: страницы метаданных и ограниченный DOM

Продолжение поручения владельца об отзывчивости от 18.10.2026.
Baseline — [текущий интерфейс в коде](ui-baseline.md), история работ —
[общий отчёт](feed-performance.md).

## Контракт

Список бесед получает дескриптор `ChatRange`, первую страницу и отдельные
счётчики текущих/архивных чатов через `chats.query`. `chats.page` возвращает
до 16 заголовков; `chats.find` находит позицию выбранной беседы. Истории
сообщений для каталога не читаются. Прежний `chats.list` сохранён как
совместимый диагностический API, экран чатов его не использует.

Чтение работает в отдельной очереди worker напрямую с настоящей `skaro.db`.
Миграция добавляет индекс `(project_id,archived,task_id,updated_at)` и
производные счётчики. SQLite triggers изменяют счётчики и ревизию в той же
транзакции, что и INSERT/UPDATE/DELETE чата. Первичная миграция индексирует
существующие метаданные один раз; пользовательские записи не переписываются.
Порядок совпадает с прежним: `updated_at DESC`, при равенстве `rowid DESC`.

Страница, её счётчики и ревизия читаются в одной read-транзакции. Ответ
с устаревшей ревизией вызывает обновление дескриптора. Факты активного агента
добавляются main-процессом только к возвращённым строкам. Проверка занятости
перед обновлением приложения использует активные сессии и больше не
перебирает сохранённые чаты всех проектов.

## Представление

Отдельный `ChatList` хранит диапазон и первую страницу; существующий
`WindowedContent` управляет видимыми строками и кешем до 12 страниц.
Полный массив заголовков удалён из состояния экрана. Строка вынесена
в отдельный компонент с прежними атрибутами, текстами, иконками и CSS.
Высота обычной строки по снятому baseline — 30 px; архивная строка
сохраняет кнопку восстановления. Внешний вид не перепроектировался.

Сохранённая выбранная беседа находится через индекс и показывается
в списке, включая позицию вне первоначальной страницы. Tab использует
существующую обработку границ виртуальных диапазонов. Во время фонового
обновления того же запроса живые строки сохраняются до замены страницы.
Клавиатурный фокус следует за идентификатором беседы при её перемещении
в сортировке: размонтирование строки не оставляет его на `body`.
Восстановление не перехватывает фокус, если владелец уже перешёл к другому
элементу. Эта логика выделена из layout в `chat-list-viewport.svelte.ts`.
Текущий/архивный фильтр, первый активный чат при первом посещении,
создание чата и архивирование сохраняют прежние действия.

## Проверки

Проверка backend на согласованном снимке настоящей `skaro.db` прошла:
63 чата, полный порядок страниц, счётчики архива/текущих бесед, архивирование,
восстановление и откат транзакции. `EXPLAIN QUERY PLAN` подтвердил чтение
через `chats_catalog_order` без временной сортировки. Снимок получен
штатным SQLite `VACUUM INTO`, данные не создавались заново. Лог:
`output/chat-catalog-store.log`.

Размеры и вид строки сняты в прежней собранной версии настоящего приложения
на изолированной копии профиля (`output/chat-list-baseline.log`,
`output/chat-list-baseline.json`). Новые runtime-проверки каталога используют
существующие чаты и настоящие операции SQLite/Electron; заглушки и
сгенерированные беседы не используются.

Сборка и проверка Svelte/TypeScript прошли без ошибок и предупреждений;
проверки изменённых файлов ESLint и размеров модулей прошли.
Штатный Electron прошёл `chat-catalog-live.spec.ts`: страницы всех 63
бесед сверены с каноническим списком; прокрутка собрала все идентификаторы;
при текущем viewport смонтировано 58 строк. Проверены переход Tab по 50
последовательным строкам, Enter, сохранённый выбор после перезагрузки,
архивирование и возврат через существующую кнопку строки. Счётчики и
новая ревизия после изменения совпали с фактическим содержимым.
Геометрия и вычисленные стили выбранной строки совпали с baseline;
снимок экрана новой версии проверен визуально.
После выделения viewport-логики проверено настоящее перемещение беседы
из глубины списка в начало через штатное обновление backend. Клавиатурный
фокус сохранился на том же идентификаторе. Лог:
`output/chat-catalog-focus-browser.log`; окончательные сборка и проверка
типов — `output/chat-catalog-build4.log`, `output/chat-catalog-types4.log`.

Окончательный Windows ASAR прошёл все шесть затронутых browser-сценариев
за 1,2 минуты (`output/chat-catalog-packaged.log`): каталог/архив/фокус,
длинная беседа с копированием 2 544 105 символов, история задачи из 777
записей, восстановление окна, локальное эхо и настоящий вопрос Codex с
барьером, перезапуском и продолжением той же native-сессии. В проверке
каталога этого прогона 64 настоящие беседы, 58 смонтированных строк.
Новая беседа добавлена настоящим Codex-сценарием вопроса, без подмены API.
Хеши main, background worker, native worker и preload в пакете совпали
с окончательной сборкой (`output/chat-catalog-package-integrity.log`).

Локальное эхо в пакете — 17,4 мс; первый контент — 1105 мс, история —
1156 мс от создания OS-процесса. В renderer остались long tasks 50, 64
и 53 мс. Эти результаты не подтверждают мгновенный холодный запуск или
отсутствие пауз. Docker Engine по-прежнему недоступен: при закрытии
настоящего приложения зарегистрирована ошибка подключения. Контейнерный
цикл не проверялся и не подменялся. Установка и публикация не выполнялись.

## Ограничения

Глубокий SQL OFFSET и подсчёт позиции выбранной строки выполняют работу
по предшествующим записям в worker. Новый контракт ограничивает размер
ответа и DOM; он не доказывает постоянное время SQL для любого объёма.
Факты live зависят от активной канонической модели в main-процессе.
Полная командная модель истории, огромные отдельные сообщения и число
этапов плана остаются отдельными направлениями исправлений.
