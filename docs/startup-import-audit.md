# Проверка ранней загрузки backend-модулей

Проверена гипотеза переноса импортов обновлений, диагностики и обработчиков
за первый `ready-to-show`. Источник замеров — тот же реальный C4-чат в
изолированной копии профиля, штатный Electron/backend. Данные и API не
подменяются. Изменение было проверено и отклонено; оно не входит в результат.

## Измерения native-контура

| Этап | До эксперимента | Пробный вариант |
|---|---:|---:|
| Размер раннего `out/main/index.js` | 107 379 bytes | 43 190 bytes |
| Первое содержимое при восстановлении, от OS-процесса | 1678,68 мс | 1340,59 мс |
| Фактическая история при восстановлении, от OS-процесса | 1721,88 мс | 2095,09 мс |
| `ready-to-show` первого проверочного окна, process uptime | 1,07 с | 0,86 с |
| Готовность обработчиков первого проверочного окна | 1,23 с | 1,58 с |

`output/boot-baseline.log` и `output/boot-native1.log`. Это отдельные прогоны
с вариацией ОС, а не статистическая гарантия. В пробном варианте trace
фиксирует загрузку runtime-модулей с 0,88 до 1,40 с. Большой модуль проекторов
и `electron-updater` ушли из прямых ранних импортов, но их работа сохранилась
в главном процессе и сдвинула готовность backend. Ускорение первого кадра
ценой более поздней готовности истории не принимается за решение требования.

Сборка, типы, lint пробного варианта прошли. Native-проверка — три сценария:
настоящий async-вопрос с барьером и перезапуском, C4-история/восстановление
окна, настоящее сообщение Codex с optimistic echo. Функциональный проход
не отменяет ухудшения времени готовности истории. Проверочный вопрос создан
отдельно; вопрос владельца в T-166 не затрагивался.

## Результат и следующая граница

Перенос импортов отменён точечной обратной правкой. Прежние изменения
`main/index.ts` из общей работы сохранены. Восстановленная сборка
[виртуализации длинных строк](inline-line-performance.md) побайтно совпала
с прежним entry и всеми 379 файлами проверенного ASAR; build и типы прошли.

Дальнейшая оптимизация должна убирать ненужные зависимости из критического
пути, а не только менять момент их загрузки. При чтении графа обнаружены
две конкретные границы для следующего исследования:

- `AgentManager` создаёт полные Claude/Codex adapter-классы в главном процессе,
  хотя запуск native-сессий уже вынесен в worker. Нужно отдельно разбирать
  metadata/status/models/auth и жизненный цикл их процессов; перенос не
  должен обходить авторизацию, обновления или завершение дочерних процессов.
- `session-log.ts` совмещает тяжёлую фабрику projectors, чтение журнала и
  лёгкие `errorText`/редактирование секретных ответов. Импорт лёгкого helper
  не должен сам по себе втягивать projectors и SDK.

После отката выполнено отдельное [разделение CLI и SDK Claude](adapter-startup-performance.md).
Оно устраняет загрузку SDK при проверке аккаунта; полный перенос metadata
в worker и дальнейшее разделение helpers/projectors пока не выполнены.
Мгновенный запуск приложения ещё не достигнут.
