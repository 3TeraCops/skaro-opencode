# Граф проекта: данные, индекс и анализаторы

Дата: 21.10.2026. Статус: реализация ведётся по поручению владельца;
проверенные результаты и оставшаяся приёмка — в [плане](project-graph-plan.md).
Часть [спецификации](project-graph.md), требования G-04—G-12, G-17—G-24.

## 1. Источники истины

| Слой          | Источник                                       | Роль индекса                                          |
| ------------- | ---------------------------------------------- | ----------------------------------------------------- |
| Архитектура   | Принятая .skaro/c4/model.json                  | Проекция элементов/отношений/views с исходными ID     |
| Реализация    | Реальные файлы выбранного checkout             | Извлечение фактов и разрешение ссылок                 |
| Документация  | Бриф, архитектура, ADR, SPEC, документы        | Структура, явные ссылки, основания и требования       |
| План          | Артефакты задач/этапов и привязки спецификаций | Документальные зависимости без выдуманной трассировки |
| Представление | Локальные настройки Skaro                      | Позиции, фильтры, раскрытия, камера; не факты проекта |

Индекс — производный удаляемый кэш. Его потеря не меняет исходники или C4.
Найденное в коде не становится принятой архитектурой автоматически.
Разбор документов не превращает свободный текст в подтверждённые calls/uses.
LLM не требуется: семантические дополнения агента оформляются обычным C4-пакетом
с основаниями, проверкой и решением владельца по существующему контракту.

## 2. Модель узлов и отношений

| Сущность      | Обязательные сведения                                                                                                              |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| GraphSnapshot | schemaVersion, generation, projectId, checkoutId, C4 revision/hash, source fingerprint, analyzer/config versions, coverage, status |
| GraphNode     | id, kind, name, qualifiedName при наличии, origin, sourceRefs, architectureState при наличии, attributes                           |
| GraphEdge     | id, source, target, kind, direction, origin, resolution, evidence[], architectureState при наличии                                 |
| SourceRef     | checkoutId, относительный путь, contentHash, диапазон при наличии, sourceKind                                                      |
| Evidence      | sourceRef, extractor/rule version, объяснение и область доказанного утверждения                                                    |
| Coverage      | найдено/разобрано/пропущено/ошибки по языкам и анализаторам, unresolved, причины/ограничения                                       |
| GraphPage     | snapshotId, queryHash, nodes/edges, cursor, hasMore, totals, omitted/aggregated и причины                                          |

ID C4 сохраняются с пространством c4:. Файлы получают file: + нормализованный
относительный путь; символы — язык, файл, квалифицированное имя, вид и устойчивый
ключ декларации. Номер строки не является идентичностью символа.
Документы используют канонический путь и ADR/SPEC ID; требование — SPEC ID + R-n.
Задачи — исходный ID, deployment instances — ID view/instance, не копия контейнера.

Перенос строк не меняет ID декларации. Переименование/перемещение файла сохраняет
идентичность только при доказанном сопоставлении; иначе удаление/добавление.
Перегрузки, анонимные функции и одинаковые имена в разных областях не схлопываются.
Unicode, регистр путей и разделители обрабатываются согласно файловой системе;
простое приведение всех путей к нижнему регистру запрещено.

Между двумя узлами допустимы разные отношения и повторяющиеся взаимодействия.
Совпадающие факты объединяют evidence, но не теряют направление/вид/состояние.
Containment, source mapping и dependency — разные типы, не взаимозаменяемые.
Самоссылки и циклы допустимы. Группы — вычисляемая проекция со списком исходных ID.
Агрегированная связь раскрывает исходные рёбра и их количество.

Базовые виды узлов: C4 element/instance, module/package/file, symbol,
API endpoint, event type, data model, deployment service, document, requirement,
task и milestone. Dependency package из manifest не означает загрузку во время исполнения.
Физические таблицы БД показываются только при явно разрешённом mapping.

Базовые виды отношений: contains, imports, exports, references, calls, inherits,
implements, handles, requests, emits, consumes, reads, writes, model-relation,
deploys, depends-on, documents, covers, governed-by и implements-requirement.
Последние виды допускаются только с явной привязкой; упоминание имени недостаточно.
Requests не приравнивается к успешной доставке; emits — к фактическому исполнению.

## 3. Достоверность и состояние

Origin: accepted-c4, extracted-code, extracted-document, analyzer-inferred.
Resolution: explicit, resolved, inferred, unresolved; это не проценты уверенности.
Каждое правило документирует, что именно подтверждено и что остаётся неизвестным.
Архитектурное current/planned не смешивается с resolution или свежестью индекса.

Статический import — явный факт зависимости. Цель вызова, однозначно разрешённая
по области/типу, — resolved с основанием. Вызов неизвестного receiver остаётся
unresolved; он не соединяется со всеми одноимёнными методами проекта.
Текстовый кандидат не включается в достоверный путь по умолчанию.

Связи из accepted-c4 показывают принятую модель, а не доказанную runtime-топологию.
Несовпадение модели/исходников становится диагностикой с источниками;
индексатор не исправляет модель и не подавляет найденное расхождение.
Устаревшая привязка SPEC сохраняет признак устаревания по существующему C4 hash.
Диагностика графа сама по себе не вводит новый блокер submit_result/merge_task.

## 4. Обязательная матрица анализаторов

| Адаптер         | Обязательные результаты                                                                                          | Явные ограничения                                                                            |
| --------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| TS/JS/TSX/JSX   | Файлы, экспорты, классы/функции, imports/references, наследование, разрешаемые calls; workspace/tsconfig aliases | Runtime import, eval, reflection и неизвестные внешние типы не угадываются                   |
| Svelte          | Компоненты, script/module-script, импорты компонентов и разрешаемые обработчики                                  | Сопоставление диапазонов с исходным .svelte; строка шаблона не становится вызовом            |
| Python          | Модули, области имён, классы/функции, импорты, наследование и статически разрешаемые calls                       | Monkey patching, динамические импорты, getattr и сложная диспетчеризация остаются unresolved |
| Django          | URLConf/include, views/handlers, модели и FK/M2M/O2O, доступные ORM reads/writes                                 | Не импортировать Django/settings и не подключаться к БД для анализа                          |
| HTTP frontend   | Статические method/path и разрешение вызова общего клиента                                                       | Динамический host/path, права и доступность API не выводятся из совпадения строки            |
| Events          | Событие, публикация, регистрация handler и обработчик                                                            | Только распознанные регистрации/константы; очередь не равна обычному call                    |
| Compose         | Сервисы, depends_on, networks, volumes, build contexts и опубликованные порты                                    | Наличие в одной сети не доказывает взаимодействие; не раскрывать секретные env               |
| Markdown/.skaro | ADR/SPEC metadata, R-n, ссылки, C4 bindings/evidence/decisions, task.spec/depends_on                             | Свободное смысловое сходство не даёт подтверждённого отношения                               |

TS использует Compiler API для разрешения символов; Svelte — compiler AST
с исходными диапазонами. Python — локальный Tree-sitter WASM и отдельный resolver
областей/импортов. Синтаксический парсер сам по себе не разрешает вызовы.
Другие языки могут быть видимы как файлы с честным отсутствием семантического покрытия.
Новые parser/grammar загружаются из пакета приложения, без сети и системного Python.

Django: распознаются прямые ссылки URLConf, include и class-based views;
динамические router/decorator покрываются только отдельными проверяемыми правилами.
Reads/writes ставятся на конкретную модель, когда receiver разрешён;
read/write всего PostgreSQL из любого импорта ORM запрещены.

Для Chatballs обязательны правила его общих HTTP-клиентов, URLConf, outbox и registry
обработчиков; для Skaro — типизированного preload IPC, main handlers и MCP handlers.
Правила выделяются в адаптеры обнаруживаемого framework/pattern, не зависят
от абсолютного пути, projectId или названия Chatballs. Версия правила входит в снимок.

## 5. Связь с C4 и сценариями

C4.code связывает архитектурный элемент с указанным файлом, но не доказывает,
что каждая функция файла реализует каждое его требование. Точный mapping
символа возможен лишь с дополнительным однозначным основанием.
Evidence/decisions и specifications проецируются без переписывания исходного смысла.
Задача связана с SPEC через явное поле; связь с конкретным символом не выдумывается.

Deployment сохраняет instances и instanceRelationships; отсутствующая однозначная
топология не заполняется «каждый с каждым». Один контейнер и его экземпляры
различимы. Planned-редакция существующего ID использует c4AtState и не стирает current.
Сценарий ссылается на исходные relationship IDs и ordinal шагов, см.
[контракт воспроизведения](project-graph-scenarios.md).

## 6. Индексация и жизненный цикл

1. Зафиксировать root/checkout, настройки, версии анализаторов и generation.
2. Перечислить допустимые файлы, вычислить manifest и прочитать валидные артефакты.
3. Параллельно в ограниченном worker pool разобрать изменённые файлы.
4. Обновить декларации/ссылки и повторно разрешить затронутые зависимости.
5. Построить межслойные связи, поиск, сводки групп и диагностику покрытия.
6. Повторно проверить generation и content hashes прочитанных файлов.
7. Атомарно опубликовать только согласованный снимок и событие готовности.

Manifest включает HEAD при наличии Git, содержимое tracked/dirty/untracked,
модель C4 и документы; HEAD недостаточен. Для каталога без Git — root identity
и content manifest. Смена ветки/worktree никогда не переиспользует снимок другого кода.
Перемещение зарегистрированного root требует повторной валидации идентичности.

Файловые события объединяются в небольшое окно; change/delete/rename инвалидируют
обратные зависимости resolver, а не только AST одного файла. Изменение tsconfig,
manifest, registry или правил даёт нужную расширенную инвалидацию.
Потеря событий watcher выявляется фоновой сверкой manifest и при возобновлении
Skaro; открытие раздела графа не является обязательным условием такой сверки.

Готовый старый снимок остаётся читаемым с отметкой stale во время обновления.
При изменении файлов во время чтения — повтор ограниченного набора либо отмена;
смесь двух состояний не публикуется как ready. Ответы старого worker отклоняются.
Отмена останавливает только индексатор/раскладку, а не агента и окружение проекта.
Закрытие раздела/вкладки проекта не отключает наблюдение и фоновые обновления.
Удаление проекта из реестра останавливает его задания/watcher и удаляет только
его кэш. Выход из Skaro освобождает workers/watchers, сохраняя состояние заданий.

Первоначальное построение запускается в фоне сразу после успешного завершения
штатного импорта: выбранные владельцем артефакты уже применены, проект зарегистрирован,
результат импорта сохранён. В этот момент автоматически ставится задание на
построение индекса и обзорного графа; открытие раздела не требуется.
Черновик, ожидание решения, отклонённый, отменённый или неуспешный импорт
не считаются завершённым импортом и не запускают первоначальное построение.

Постановка задания сохраняется и идемпотентна по операции импорта/project/checkout;
повтор события или восстановление применения не создают дублирующих построений.
Обработчик успешного импорта ставит задание, не ожидая завершения индексации.
Ошибка индексатора не откатывает успешный импорт: сохраняется диагностика и
возможность повторного построения. Частично построенный снимок не выдаётся за ready.

После импорта код, документы и принятая C4 наблюдаются для зарегистрированного
проекта, даже если выбран другой проект или раздел графа ни разу не открывался.
Подключение уже существующего проекта через реестр также запускает чтение его
реальных исходников и принятых артефактов. Незавершённый импорт документации
не становится источником графа: черновики импорта исключены, успешное применение
пакета отдельно инициирует обновление после сохранения результата.
Изменения автоматически ставят инкрементальное обновление с debounce и ограничением
фоновой нагрузки. Отрисовка Sigma начинается при открытии, но не запускает
первоначальную индексацию и не является условием актуализации данных графа.

При старте Skaro восстанавливаются незавершённые задания и сверяются manifest
импортированных проектов, включая проекты без готового индекса. Изменения,
сделанные при выключенном Skaro, автоматически догоняются в фоне. Недоступный
корень помечается недоступным; его старый граф не объявляется актуальным.
Старт интерфейса не ожидает построений и не запускает проектные сервисы.

## 7. Хранение и разделение процессов

Предлагается отдельный SQLite-кэш под каталогом данных Skaro:
graph/<projectId>/<checkoutId>/index.sqlite. Схема версионируется; несовместимый
производный кэш перестраивается, C4/документы и данные приложения не мигрируют.
Таблицы: snapshots, files, nodes, edges, evidence, unresolved, coverage и search.
Индексы: source/target/kind/snapshot, path, qualifiedName; локальный поиск — FTS
при поддержке упакованного SQLite, иначе эквивалентный индекс без сканирования renderer.

Main проверяет полномочия/корень и управляет заданиями. Тяжёлый индекс работает
в отдельной фоновой очереди, не в общей очереди сохранения C4/ответов владельца.
Renderer получает только DTO. Layout worker видит разрешённый подграф/координаты,
не файловую систему. Sigma/Graphology не служат хранилищем всего проекта.

Worker подготавливает неизменяемый снимок транзакционно. Только планировщик main,
после проверки актуальной generation, меняет указатель опубликованного снимка.
Отменённая или завершившаяся по таймауту работа не может переключить указатель.
Текущий и предыдущий опубликованные снимки сохраняются. Очистка остальных
выполняется после события готовности, порциями в фоновой очереди, и переживает
прерывание через журнал удаления. Запросы читают согласованный SQLite/WAL-снимок;
истёкший snapshotId отклоняется, а не возвращает частично удалённые данные.

Реализованные IPC-контракты:

| Метод                                       | Результат/ограничение                                              |
| ------------------------------------------- | ------------------------------------------------------------------ |
| graph.status / graph.rebuild / graph.cancel | Покрытие, generation, progress и отмена задания                    |
| graph.query: overview / expand              | Агрегированный обзор/раскрытие с курсором                          |
| graph.query: search / details               | Страница результатов/детали по ID и snapshot                       |
| graph.query: neighbors / path / impact      | Направление, фильтры, budgets, результаты и completeness           |
| graph.scenarios / graph.model               | Каталог, валидированные шаги и C4 на одном snapshot                |
| graph.source / graph.view / graph.saveView  | Проверенное открытие диапазона / локальное состояние представления |

Запрос содержит projectId, checkoutId, snapshotId и requestId; scope проверяется
в main. Ответ содержит тот же snapshotId и валидированный cursor, привязанный
к фильтрам/области. Устаревший cursor не возвращает страницу из нового снимка.
Предварительные ограничения: 500 узлов/2000 рёбер на страницу, 100 результатов
поиска, 5000 узлов/20000 рёбер материализованного обзора; расширение — порциями.
Это бюджеты отображения, не усечение индекса; число скрытого видно и доступно обходу.
Path/impact ограничены посещениями/временем; исчерпание возвращает incomplete.

## 8. Безопасность, ресурсы и переносимость

Root канонизируется через realpath; symlink/junction за его пределы не обходится.
Git submodule не сканируется вне явно разрешённых корней. Учитываются .gitignore
и встроенные исключения dependencies/build/.git/caches; tracked-файлы и .skaro
читаются согласно явному source policy. Секреты, .env, бинарные файлы, vendor,
медиа и сгенерированные bundle исключены по умолчанию с причинами в coverage.
Ограничиваются размер файла, глубина, число файлов, AST, память и длительность задачи.
Пропуск лимита видим, а не считается успешным разбором.

Не исполняются import, eval, tsconfig plugins, lifecycle scripts, Django setup,
Compose, MCP-серверы и код из документов. Заголовки/labels отображаются как текст.
В кэш не копируются полные тела исходников, значения секретов и env;
при открытии source проверяются путь и hash, изменённый диапазон не выдаётся за прежний.
Кэш и IPC не содержат tokens из настроек интеграций, URL credentials очищаются.

Проверяются Windows/macOS/Linux, x64/arm64 согласно release matrix проекта:
пути, Unicode, доступность WASM/worker assets, SQLite и упаковка без devDependencies
внешнего checkout. Сеть для обычной индексации не нужна. Ресурсные цели и
доказательства — в [плане проверки](project-graph-plan.md#8-приёмка-и-проверки).
